# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Smart Kirana Store — an offline-first Flutter app for managing a grocery/kirana store (billing, products, purchases, reports, customers). Android is currently the only configured platform (no ios/windows/macos/linux/web directories exist yet).

All 13 planned modules are done (Project Setup, Database Foundation, Auth, Dashboard shell, Products, Purchase, Billing/Sales, Customers, Stock history, Dashboard live data, Profit & Loss, Reports, Settings) — every Dashboard quick-nav tile and every Reports-hub tile now opens a real screen; there are no remaining "coming soon" placeholders. Explicitly out of scope / simplified by design (see the conversation that built this): camera barcode scanning (barcode is a plain text field), weighted-average purchase costing (last-purchase-price wins instead), credit/dues/partial-payment tracking, per-line billing discounts (bill-level percent only), and store-logo image upload/rendering.

## Commands

```
flutter pub get                     # install dependencies
flutter run                         # run on connected device/emulator
flutter test --concurrency=1        # run all tests (see note below — required)
flutter test test/widget_test.dart  # run a single test file
flutter analyze                     # static analysis / lints
flutter build apk --debug           # build a debug APK (no signing needed)
flutter build apk                   # build Android release APK
```

There is no CI config, no lint-fix script, and no custom build tooling beyond the standard Flutter CLI.

**Local dev environment note**: Flutter SDK lives at `C:\src\flutter` (not on PATH by default) and `JAVA_HOME` must point at `C:\Program Files\Eclipse Adoptium\jdk-17.0.19.10-hotspot` for Gradle/Android builds — see the `build_environment` memory for full details (device serial, adb path, etc.) if picking this project back up in a new session. `android/gradle.properties` sets `kotlin.incremental=false` to work around a Kotlin/Gradle crash that happens when the project drive and the Flutter/Gradle cache drive differ (D: vs C: here) — don't remove that line. It also pins `android.builtInKotlin=false`/`android.newDsl=false` (Flutter-template defaults) — leave these as `false`; setting `builtInKotlin=true` breaks `flutter_plugin_android_lifecycle` under this Flutter version's AGP. `pubspec.yaml` has a `dependency_overrides` pinning `flutter_plugin_android_lifecycle` to `2.0.24` — newer versions require `compileSdk 36`-compiled dependents and broke `file_picker: ^8.3.7`'s AAR metadata check; don't remove the override without re-verifying a clean `flutter build apk`.

## Architecture

- **Local-first persistence**: `sqflite` is the primary data store. The full schema (11 tables: `users`, `categories`, `products`, `product_price_variants`, `customers`, `purchases`, `purchase_items`, `sales`, `sale_items`, `stock_history`, `store_settings`) lives in [lib/database/app_database.dart](lib/database/app_database.dart) (singleton, `onCreate`/`onConfigure`/seeding) and [lib/database/db_tables.dart](lib/database/db_tables.dart) (column-name constants). `shared_preferences` is used only for small key-value settings (theme mode, persisted login flag — keys in `AppConstants`). No backend/API layer exists.
- **Multi-pricing / box-pricing data model**: a product's sellable price options (e.g. Sugar's 1kg/500g/250g/100g, or a Box vs a loose Packet) are all rows in `product_price_variants`, not separate tables. Every product has one `base_unit` and `current_stock` is always expressed in it; each variant's `quantity_in_base_unit` converts to/from that. "Remaining boxes vs packets" must always be computed from `current_stock` at display time — never store it separately, or it will drift.
- **Stock integrity rule**: only repository code (`purchase_repository`, `sale_repository`, `stock_history_repository` — added in later modules) may write `products.current_stock`, always inside a `db.transaction`, always paired with a `stock_history` row. Providers/UI never touch stock directly.
- **State management**: `provider`, via one `ChangeNotifier` per feature registered in `main.dart`'s `MultiProvider` (currently `ThemeProvider`, `AuthProvider`). `AuthGate` ([lib/screens/auth/auth_gate.dart](lib/screens/auth/auth_gate.dart)) swaps between the Login screen and the post-login home based on `AuthProvider.isLoggedIn` — no explicit navigation needed for login/logout, just provider state changes.
- **Auth**: single admin account, seeded by `AppDatabase` with `AppConstants.defaultUsername`/`defaultPassword` (SHA-256 hashed via [lib/utils/password_hasher.dart](lib/utils/password_hasher.dart) — no per-user salt, since there's no server round-trip to protect against, only this device's own DB file). Login session persists across app restarts via `AppConstants.prefKeyIsLoggedIn`. Offline "forgot password" is a security-question flow ([lib/screens/auth/forgot_password_screen.dart](lib/screens/auth/forgot_password_screen.dart)) set up from Account Settings — if no question is configured yet, the recovery screen just says so and sends the user back to log in normally.
- **Localization**: `easy_localization` drives all user-facing strings, loaded from `assets/translations/{en,mr}.json` (English and Marathi). Any new UI text must be added to both JSON files under the appropriate nested key (`common`, `settings`, `nav`, `auth`, `home`, etc.) and referenced via `'key.path'.tr()`, never hardcoded. Provider `errorMessage` fields hold translation *keys* (e.g. `'auth.invalid_credentials'`), not display text — screens call `.tr()` on them, keeping providers free of localization/BuildContext concerns.
- **Theming**: centralized in [lib/core/theme/app_theme.dart](lib/core/theme/app_theme.dart) via `AppTheme.lightTheme`/`AppTheme.darkTheme`. Both are Material 3, generated from a single seed color (`AppTheme.seedColor`, grocery green). `ThemeProvider` persists the user's light/dark/system choice; update the seed/theme itself in `AppTheme`, not per-widget.
- **Constants**: app-wide constants (db name/version, default admin credentials, shared_preferences keys) live in [lib/core/constants/app_constants.dart](lib/core/constants/app_constants.dart) as static members on a private-constructor class — the same pattern is used for DB table/column names in `db_tables.dart`.
- **Entry point**: [lib/main.dart](lib/main.dart) wraps the app in `EasyLocalization`, then `SmartKiranaApp` builds a `MultiProvider` (each provider's `create:` calls `..initialize()` to restore persisted state asynchronously) feeding a `Consumer<ThemeProvider>` that builds `MaterialApp` with `home: const AuthGate()`.
- **Widget tests**: because `easy_localization` reads persisted locale via `shared_preferences`, and `AuthProvider.initialize()` reads the persisted login flag the same way, any widget test that pumps `SmartKiranaApp` must call `SharedPreferences.setMockInitialValues({})` before `EasyLocalization.ensureInitialized()` — otherwise the platform channel call never resolves and `pumpAndSettle` hangs indefinitely (see [test/widget_test.dart](test/widget_test.dart)).
- **Database tests**: [test/database/app_database_test.dart](test/database/app_database_test.dart) overrides sqflite's global `databaseFactory` with `sqflite_common_ffi` so schema/seed/cascade behavior can be verified against a real SQLite engine on the desktop test host, without needing a connected Android device. All repository tests do the same and share one fixed on-disk file (`AppConstants.databaseName`, deleted/recreated in each test's `setUp`) — `flutter test`'s default concurrency runs test files in parallel processes, which collide on that shared file with "database is locked" errors. Always run tests with `--concurrency=1`.
- **Purchase module transaction pattern**: `ProductRepository.adjustStock` takes an optional `executor` (`DatabaseExecutor?`) parameter — pass the caller's own open `Transaction` when one is already held (e.g. `PurchaseRepository.createPurchase` inserts the purchase + each line item + calls `adjustStock(..., executor: txn)` all inside one `db.transaction`). Without this, calling `adjustStock`'s default (which opens its own `db.transaction`) from inside another transaction deadlocks — sqflite serializes transactions on one connection. Any future module (Sale) that mutates stock inside a larger transaction must follow the same pattern.
- **Purchase line items aren't tied to product variants**: `purchase_items.variant_label`/`conversion_factor` are plain snapshot columns, not a FK to `product_price_variants` — a purchase can be recorded in the product's raw base unit *or* any of its sellable variants (see the unit dropdown in `lib/screens/purchase/widgets/purchase_line_item_editor.dart`), so buying loose bulk works even for products only ever sold in fixed pack sizes. `products.purchase_price` is last-write-wins (`price_per_unit / conversion_factor` of the most recent purchase line for that product) — not a weighted average.
- **Billing math (discount before GST)**: `lineSubtotal = qty * unitSellingPrice`; `lineDiscount = lineSubtotal * discountPercent / 100`; `lineTaxable = lineSubtotal - lineDiscount`; `lineGst = lineTaxable * gstPercent / 100`; `lineTotal = lineTaxable + lineGst`; `lineProfit = lineTaxable - (qty * conversionFactor * unitPurchasePrice)` (GST is never revenue, so it's excluded from profit). Bill-level totals are sums of these per-line values (never `subtotal * rate` shortcuts), so the footer always matches what the printed line items add up to. Unlike Purchase, Billing's unit picker (`lib/screens/billing/widgets/billing_variant_picker_dialog.dart`) only offers active `product_price_variants` — no raw-base-unit option — because only variants carry a `selling_price`; a product with zero active variants can't be billed until one is added.
- **Invoice numbering is atomic**: `SettingsRepository.takeNextInvoiceNumber` reads and increments `store_settings.last_invoice_number` and must only ever be called from inside `SaleRepository.createSale`'s own transaction (it takes a required `executor`, no standalone mode) — that's what prevents two sales from ever getting the same invoice number.
- **Overselling is allowed by design**: Billing's cart warns (red text under the line) when a cart line's quantity exceeds `current_stock`, but never blocks checkout — real shops often sell against approximate/uncounted stock, so `adjustStock` is allowed to go negative.
- **PDF invoices**: `lib/services/pdf_service.dart` uses `pdf`+`printing` (`Printing.layoutPdf` opens the OS print/share sheet — no separate preview screen). Marathi invoices swap the whole document's font to a bundled `assets/fonts/NotoSansDevanagari-Regular.ttf` (the `pdf` package's default font has no Devanagari glyphs) based on a plain `languageCode` string the caller passes in — `pdf_service.dart` itself never touches `easy_localization`/`BuildContext`.
- **Customers are hard-deleted, products aren't**: `sales.customer_id` is `ON DELETE SET NULL` (unlike `sale_items.product_id`, which has no cascade and relies on products being soft-deleted via `is_active`), so `CustomerRepository.deleteCustomer` really deletes the row — past invoices just lose the customer link and read as a walk-in sale, nothing breaks. `customers` has no stored running total either — `total_purchase_amount` is always `SUM(sales.total_amount)` computed at query time, same non-drift rationale as `product_price_variants`' computed box/packet breakdown.
- **Stock history/adjustment is UI-only, not new write logic**: `StockHistoryRepository` ([lib/repository/stock_history_repository.dart](lib/repository/stock_history_repository.dart)) is read-only by design — every write to `stock_history` already happens through `ProductRepository.adjustStock` (purchase, sale, or the "Current Stock" field on Edit Product, which calls `ProductProvider.adjustCurrentStock`). The ledger view is reached via a history icon in `ProductFormScreen`'s app bar (edit mode only); there's no separate "Stock Adjustment" screen because editing a product's Current Stock field already is that flow.
- **Dashboard/Reports share one query layer**: `ReportRepository` ([lib/repository/report_repository.dart](lib/repository/report_repository.dart)) is written to be reused by Dashboard's "today" stats and Reports' arbitrary date ranges — keep new report queries in this one file rather than duplicating them into a separate dashboard-only repository. "Today"/date-range filters use `date(column) BETWEEN date(?) AND date(?)` (inclusive both ends), matching that `DateTime.now().toIso8601String()` (used everywhere sale/purchase dates are stored) is local time, not UTC — always pass plain `DateTime`s and let SQLite's `date()` truncate them. Profit/loss are never `total_profit`'s sign averaged — each sale's `total_profit` is bucketed independently (positive sales sum into profit, negative sales sum into loss), so a single day/month/year can show both a nonzero profit and a nonzero loss if some bills were sold below cost. Stock value is valued at cost (`current_stock * purchase_price`), not at selling price, since selling price only exists per-variant.
- **Profit & Loss periods are "period to date"**: `ReportsProvider.rangeFor` computes Day = today, Month = 1st of this month → today, Year = Jan 1 → today (not full calendar month/year), since there's never future sales data to include anyway. `ReportRepository`/`ReportsProvider` are shared by both the Profit & Loss screen and the Sales Report screen — extend this one repository/provider for new report queries rather than creating a parallel one.
- **PDF export is one shared method, not per-report layouts**: `PdfService.buildSimpleReportBytes` (title/columns/rows/optional total row) backs every tabular report — Stock/Product Report (`ProductsListScreen`'s app-bar PDF icon), Customer Report (`CustomersListScreen`), Purchase Report (`PurchaseListScreen`), and the Sales Report screen. Only the invoice PDF (`buildInvoiceBytes`) has its own bespoke layout, since it needs a store-info header and a totals block that a generic table doesn't. Both share the same Marathi-font-swap helper (`_themeFor`).
- **Backup/restore uses bytes, not raw paths**: `BackupService` ([lib/services/backup_service.dart](lib/services/backup_service.dart)) always moves file content as `Uint8List` through `file_picker`'s `saveFile(bytes: ...)`/`pickFiles(withData: true)` rather than assuming a picked path is a plain filesystem path — Android's scoped storage means it often isn't. Restore closes `AppDatabase` before overwriting the file (via `AppDatabase.instance.databasePath`) and then exits the app (`SystemNavigator.pop()`) since the restored data only takes effect on a fresh app start. `SettingsRepository.update()` only ever touches store-info columns, never `invoice_prefix`/`last_invoice_number`.
